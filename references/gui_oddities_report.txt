5h. [MEASURE]'s REAL per-die measurement loop silently falls back to fake
    randomized readings when hardware isn't connected - a different,
    live "sim" path from the dead [SIM REMOVE]/ExecutionDashboard one
    File: gui/instrument_panel.py, _exec2_run_steps_once (~line 6027-6097
    onward) and its per-step-type sim fallbacks throughout
    Found: 2026-09-05

    Unlike item 5c's dead ExecutionDashboard "sim" demo mode, this is a
    LIVE code path inside the real Run tab's measurement loop. Whenever
    the switch matrix (or a given step's instrument) isn't connected, `sim`
    is set True and every measurement in that iteration reads back a fake
    value instead (e.g. voltage/current steps use `random.gauss(3.3, 0.1)`
    or similar synthetic noise around the nominal level, current-apply
    readback synthesizes a value near the commanded level with a tiny
    gaussian jitter). The only indicator in the log is a small suffix on
    ONE line - "[MEASURE] One iteration — {N} step(s)  [SIM — no switch
    matrix connected]" - easy to miss, and none of the individual R=/V=/I=
    lines that follow are marked as simulated themselves. Worth deciding
    whether every simulated reading line should carry its own visible
    marker (not just the one summary line at the top of the iteration),
    since a user skimming mid-log could otherwise mistake fabricated data
    for a real measurement.

8. Recipe tab - "ohmf" (4-wire resistance) steps are fully buildable but
   never actually execute
   File: gui/instrument_panel.py (_exec2_run_steps_once, ~line 6014-6566)
   Found: 2026-09-07

   The Recipe tab's step editor fully supports "ohmf" as a Type: it has its
   own SnsHI/SnsLO sense-pin fields (recipe_panel.py's FOUR_WIRE_TYPE),
   restricts the Instrument choice to DMM only (_instrument_options), and
   validate_recipe()/Compute Connection are aware of it. But the actual run
   engine's step dispatch (_exec2_run_steps_once) only branches on
   t == "delay" / "move" / "picture" / "open" / "passfail" / "resistance" /
   "voltage" / "current" / "wave" - there is no "ohmf" (or FOUR_WIRE_TYPE)
   branch anywhere in gui/instrument_panel.py at all (confirmed: zero
   matches for "ohmf", "FOUR_WIRE_TYPE", "his", or "los" in that file).

   Concretely, an "ohmf" step in a real run: still gets its switch channels
   closed (that happens generically before the type dispatch, for every
   step), gets no instrument command sent, takes no reading, records no
   result, and the loop silently moves on to the next step - no error, no
   log line calling out that it did nothing beyond the generic "close
   conn" line every step type gets.

   Level/Limit/HI/LO/SnsHI/SnsLO can all be filled in for an ohmf step and
   look completely normal in the editor and in a saved recipe - there is
   currently no way to tell, short of reading this code, that the step
   will do nothing when the recipe actually runs. Needs a decision: add
   the missing execution branch (real 4-wire DMM resistance read), or
   remove "ohmf" from the Type list until it's implemented.

   File: gui/recipe_panel.py (_build_shot_origin_controls /
